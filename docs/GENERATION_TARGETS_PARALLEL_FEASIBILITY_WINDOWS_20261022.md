## 原型与正确性边界

`scripts/experiments/generation_parallel.py` 从当前 `generate_v61` 的 AST 直接提取生产逐字代码，初始化相同的真实档案、修正结构库、语义生成器、NumPy 批量回退和扩展策略。没有另写一套简化生成算法。原型与正式串行路径先以 11 字逐字段核对：供体、候选证据、接受/拒绝、轨迹、压力、时间、来源缺口、规则日志、检查结果均一致。

生产函数会把初始化规则证据放在首字日志；原型为每个计算单元单独保存此证据，并在逐字任务开始时清空其日志。本次真实档案的初始化前缀为空，所以无需删除任何实际逐字证据即可完全一致。取消仍以字为边界。

线程使用各自独立引擎。不能共享引擎的源码依据包括：语义回退暂时改写 `pool` 与 `descriptors`，生成器改写 `semantic_log`、`rule_log`、结构缓存及规则图缓存。进程使用 Windows `spawn` 和持久初始化器；不为每个字重载全部资源，不加入单字内部候选并行。

每个字写独立文件，IPC 仅传回身份、检查摘要和计时；逐点轨迹不通过进程队列往返。父进程按请求顺序汇总，完成顺序不参与选择。当前 SQLite 查询各自打开和关闭连接，没有跨进程传递连接。每计算单元仍保留生产路径每 100 字清理缓存的规则；本轮没有完成超过 100 字的单个持久工作进程边界测量，此点列为后续验证项。

## 字集模型

现有桌面入口已支持指定目标字符串及全结构库目标；其去重方式保留首次出现顺序。源码中的 GB2312 / 非 GB2312 分包不是完整简体 / 繁体分类，不能把其补集当作繁体字集。

实验目标清单包含字表名称、版本/来源、实际 Unicode 字符序列、内容哈希、支持与不支持字符、稳定合并顺序以及完整供体范围。缩小目标只减少输出工作，**不缩小作者供体池**。

- 大陆规范字代表子集：2013《通用规范汉字表》序号 0001—0004，通过 [Unicode 的 kTGHZ2013 原始提案附表](https://www.unicode.org/L2/L2019/19160-adding-ktghz-2013.pdf)核对索引文字。完整官方附件未成功获取：网页重定向/403、PDF 过大及下载握手超时均有记录，不能宣称已经核实完整规范字表。该子集只有四字，不代表简体特有字覆盖。
- 台湾常用国字代表子集：[教育部官方比对表](https://language.moe.gov.tw/001/Upload/files/SITE_CONTENT/M0001/PRIMARY/shrest2-18.htm)的前 28 项，保留标准字表编号。官方说明对应 1982 年公告的 4,808 字表；本轮只核对这 28 项，不把它称作完整繁体或所有地区异体集合。
- 简繁共用字允许同时属于多个字集，合并时只去重，不从任何字集中删掉共用字。自定义回归保留 `发/發/髮`、`台/臺` 各自身份，不做简繁转换、Unicode 归一化或正文替换。一简多繁和地区异体的完整归属数据仍需独立引入权威、版本化字表。
- 单 Markdown 使用当前解析器的文本、公式汉字、字段、代码和图题等印刷文本节点及准确源码范围；URL 和图片文件路径不作为生成目标。对实际已有的 8,275 字符多页文档 `artifacts/preview_performance_0.1.12_20261018/input.inkdoc` 提取到 345 个独立汉字，全部受结构库支持；生成测量明确只取其中前 8 个，未宣称生成全部 345 字。原文档及其缺字/公式诊断保持不变。另用真实纯符号文档验证空汉字目标不会启动生成任务。
- 解析提取是保守的印刷节点集合。正式接入时还应结合当前模板字段可达性、图题开关及布局诊断校验“实际使用”，不能将未用字段或关闭的图题误称为必需生成内容。
- 全支持字集保存完整 9,574 字清单，实际计算仅用明确记录的代表集合；没有完成 9,574 字全库新生成或完整字表 GUI。

另验证带变体选择符的汉字序列作为完整单位报告不支持，不拆成普通汉字后静默生成，更不修改原文。

`target-sets.json`、`real-markdown-targets.json`、`scope-inputs.json` 保存实际字符与身份。空字表、去重、稳定顺序、字集合并、不支持项、源码定位均有断言。不同范围中相同汉字逐字段比较，检验目标范围与供体选择无关。

## 阶段瓶颈

在独立插桩进程中，仅增加计时作用域，保持原计算和早返回行为；该轮结果同样参与完整内容一致性比较。计时为包含子调用的 inclusive 时间，**不可相加**。

11 字插桩运行：初始化约 14.31 秒，逐字生成与写出约 17.45 秒。结构库逻辑内容哈希调用 11 次、累计约 20.13 秒；JSON 编码约 10.99 秒/105,425 次，结构 SQL 读取与解码约 6.58 秒/3,576 次，二者与逻辑哈希等阶段重叠。

初始化包含修正资源校验约 2.14 秒、主引擎初始化约 6.53 秒、笔画池与描述符约 3.23 秒、档案读取解析约 0.31 秒。主引擎/回退等初始化还会校验档案与结构库身份；羊部件特殊分支重新构造旧规则引擎，再次触发这些逻辑哈希。没有为了加速取消任何一次现有校验。

当前 NumPy 批量拟合数组计算约 **0.0060 秒**，候选准入过滤约 0.0305 秒，排序约 0.00072 秒，最终候选几何复核约 0.125 秒；语义选择整体约 0.363 秒。输出压缩约 0.043 秒，二进制写出约 0.0068 秒，输出/档案文件哈希包装约 0.076 秒，来源完整性约 0.0039 秒。不能把 CPU 总占用较低解释为需要 GPU，也不能把优化这几毫秒描述成全库生成显著提速。

11 字暖串行样本中，“羊”约 8.21 秒、“群”约 9.37 秒，其余九字合计约 1.07 秒。这解释了为何 11 字上四进程相对二进程几乎没有额外收益；它不是均匀任务分布。

### IPC 与汇总

补做 32 字、四进程两批的分段试验，使用同一系统单调时钟标记投递、计算入口、资源就绪、返回字典就绪和父进程接收。64 个返回字典序列化约 558—618 字节，不传递完整轨迹。

“返回就绪→父进程接收”中位约 **0.392 ms**，P95 约 **0.95 ms**，最大 4.23 ms；包含序列化、管道、Future 分派和父进程唤醒，不能称为纯传输线耗时。单进程资源初始化约 16.75—17.00 秒；冷投递等待包含它和队列排队。两次结果汇总/协议写出分别约 26.7、14.6 ms，工作池关闭约 1.14 秒。原始跨进程时间戳和队列等待在 `transport-stages/transport.json`。

32 字、四进程该附加试次的首批 27.66 秒、暖批 9.93 秒，单列为插桩试验，不用它替换上表中更慢的正式重复样本。当前主要瓶颈不是这种摘要 IPC；若以后传输完整轨迹，需要重新测量，不能沿用此结论。
