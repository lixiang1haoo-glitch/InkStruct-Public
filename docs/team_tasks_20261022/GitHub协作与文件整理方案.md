# InkStruct GitHub 协作与文件整理方案

日期：2026-10-22。面向组长及两个开发小组。本方案落实五人分工：主线与字集研究共享核心代码，Android 独立开发，通过固定版本的协议与真实样本联调。

## 一 当前核查结果

- 已连接账号为 `lixiang1haoo-glitch`，该连接当前未返回所属组织。
- 账号已有私有仓库 [InkStruct](https://github.com/lixiang1haoo-glitch/InkStruct)，默认分支为 `main`，账号具有管理权限。远端 README 仍描述较早的 v4 流程，远端当前未找到 `src/inkstruct/fonts/__init__.py`；不能把它当作已同步的 0.1.40 基线。
- 本地分支为 `codex/v61-starter-collection`，HEAD 为 `af45b45f04f899fcaced43aa980b0508673ee6c0`，有 80 个可达提交，本地没有配置 Git remote。当前大量应用文件是未提交修改或未跟踪文件。
- 本轮清单覆盖 Git 已跟踪文件和未忽略的未跟踪文件，不遍历或复制已忽略的用户数据。在增加本方案文件之前，清单包含 983 个待审源码候选、1 个第三方 gitlink，以及应排除的 20 个迁移／用户文件。候选约 18.34 MB，排除部分约 56.58 MB；数量会随之后新增文件变化。
- `handoff/` 中存在原始录制 ZIP、作者索引、历史 bundle 和工作区快照；`检查项目/` 含用户评价。它们未被当前忽略规则整体排除，不能直接 `git add .`。

清单与哈希位于 `artifacts/github_collaboration_20261022/`。文件分类是迁移候选，不等于已完成逐文件发布审核；有限凭据模式检查没有命中，也不代表可以省略内容与授权检查。本轮没有暂存、提交、创建远端仓库或上传文件。

## 二 建议使用两个私有仓库

| 仓库 | 内容与职责 | 使用人员 |
| --- | --- | --- |
| 沿用 `lixiang1haoo-glitch/InkStruct` | Python 核心、桌面、字集研究代码、评测脚本、任务书、公共协议与测试 | 组长、字集组；Android 组读取协议并参与联调 |
| 新建 `lixiang1haoo-glitch/InkStruct-Android` | Android 源码、构建配置、移动端测试、批次接收原型、平台使用说明 | Android 组主开发，组长审核，两组共同验收 |

两组共同负责的协议以主仓库为唯一维护源。Android 固定引用主仓库的具体提交和协议版本，并带少量合成测试样例；不要在两个仓库各自维护一份可独立修改的正式协议。主仓库的应用版本源仍为 `APP_VERSION`，Android 构建从指定基线读取版本，禁止复制硬编码后自行漂移。

字集研究需要频繁调用当前生成代码和资源，因此暂不另设研究仓库。协议规模较小，也暂不增加独立协议仓库。作者数据和大批生成结果采用单独受控文件分发，不默认新建“数据 Git 仓库”。

如果需要彻底保留旧远端不动，可将第一项改成新建 `InkStruct-Team` 私有主仓库；原仓库只作历史参考。如果团队更重视一个 PR 同时修改接口和两端实现，可以改为单仓库 `android/` 子目录。当前默认建议仍为沿用主仓库加独立 Android 仓库。

## 三 文件如何归类

**进入主仓库的候选内容：**`src/`、`tests/`、`scripts/`、`configs/`、`packaging/`、`examples/`、文档源码、项目配置、启动脚本和许可文件。保留 `third_party/makemeahanzi` 的固定子模块提交及 `.gitmodules`，不把已有上游目录误当普通文件全部重新上传。

其中 `configs/collection/` 可以保留推荐任务和方法报告；带作者 ID 的历史报告、论文和截图需核对是否适合全员共享。测试样例和图表只保留可说明来源的最小材料，不把真实作者大批轨迹包装成 fixtures。

**通过资源包或可复现构建提供：**结构数据库、与生成基线一致的笔顺参考、外部桌面采集内核，以及少量获准参与研究的真实作者样本。包内记录版本、SHA-256、来源与访问范围，源码仓库保存资源清单和获取／重建方式。可重建结构库优先保留构建命令，同时固定上游和修正规则身份。

当前 `artifacts/external/data_collection/handwriting_collector/` 实际承担桌面采集依赖。整理时必须为它明确来源、权属和交付方法，不能因为所在目录被忽略就当作纯缓存省略。短期可用受控依赖包；如确认应长期维护，再单独讨论纳入主仓库或正式依赖。

**保留本地并从上传候选排除：**`handoff/`、`检查项目/`、原始作者样本、`profiles/`、`outputs/`、`workspaces/`、虚拟环境、模型权重、构建缓存、历史发布包、个人环境变量和密钥。排除只改变上传范围，不删除或移动原件。

GitHub 建议生成物存放在 Git 之外，并对普通 Git 对象设置大小限制。当前应先按内容和用途分类；不要为迁移快照中的样本启用 LFS 后就整包上传。[GitHub 仓库限制](https://docs.github.com/en/repositories/creating-and-managing-repositories/repository-limits)

## 四 整理与迁移步骤

1. 固定当前清单和文件哈希；保留原工作区及历史交付。使用独立整理副本，不对当前工作区执行 reset、clean、历史重写或批量移动。
2. 对 983 个源码候选做内容与依赖复核，补上任务文档及后续新增文件；把用户资料、凭据和迁移快照排除。对本地历史另做检查，确认历史中是否包含不应上传的文件；不能只检查当前目录。
3. 在整理副本完善忽略规则，明确排除 `handoff/` 与 `检查项目/`。整理现有 README、CONTRIBUTING 和安装入口，确保默认桌面／研究环境不强制安装训练 CUDA 依赖，也不清空已有虚拟环境。
4. 拉取已选远端到独立副本，记录实际远端 main 提交，检查与本地历史的共同祖先。存在共同祖先时优先保留历史，在新迁移分支提交当前源码；无共同祖先时先确定导入策略，不强推覆盖远端 main。
5. 主仓库先提交可审阅迁移分支和 PR。内容包括应用当前源码、字集研究入口、接口文档、任务书、资源获取方式和协作模板；原始作者资料不进入该 PR。
6. 在选定账号下创建 Android 私有仓库，先提交任务书链接、主仓库基线身份、构建结构、忽略规则和合成协议样例，随后开发原型。任务书不等于已实现 Android 应用。
7. 对主仓库做全新 clone 验收：初始化固定子模块、安装 CPU 桌面依赖、取得已声明资源、运行代表性测试和小型 v6.2 流程；对 Android 验证可构建骨架与任务接口。
8. 验证远端均为私有、迁移内容正确后，再安排成员访问。四名成员的 GitHub 用户名与邀请范围由组长提供；不猜测账号，不在本轮发送邀请或通知。

该顺序避免成员拿到一个“源码已上传但资源来源未知、实际无法运行”的仓库。迁移 PR 的验证范围要写清：构建／协议检查不能冒充真机采集和写字机验收。

## 五 协作规则

- 默认分支统一 `main`；成员用短期分支开发，通过 PR 合并。两个小组分别维护自己的功能目录，公共协议与生成核心由组长复核。
- 主仓库使用 `collection`、`evaluation`、`protocol`、`integration` 标签；Android 仓库使用 `input`、`storage`、`ui`、`device-test` 标签。标签是本轮建议设置，不代表远端已创建。
- 每个 Issue 写目标、负责人、依赖、交付文件和验收命令；M0 至 M3 对应里程碑。跨仓库问题互相引用，记录使用的提交，避免只写“最新版”。
- PR 模板要求列明行为变化、测试、数据与协议影响、失败及限制。涉及协议时给出双方兼容样例和迁移方式。
- 常规代码至少由另一名成员审阅，主线和协议由组长最终合并。权限与平台套餐允许时开启分支保护；不能把 CODEOWNERS 文件本身当成已强制阻止直接推送。
- GitHub Free 支持私有仓库协作者；私有仓库的分支保护可用性取决于套餐，不能默认已经具备强制审阅能力。暂不因本方案增加付费订阅。[私有仓库协作者](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/repository-access-and-collaboration)；[分支保护支持范围](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)

## 六 下一步需要确定的项目

仓库布局选择为：沿用 InkStruct 加 Android、新建两个仓库保留旧仓库，或单仓库。账号目前可直接使用 `lixiang1haoo-glitch`；没有组织的必要时不增加组织管理。成员用户名可在源码整理期间补齐，邀请不阻塞本地整理。

GitHub 连接当前提供读取、文件提交、分支和 PR 等工具，但未提供新建仓库的操作；本机也未发现 `gh` 命令。布局确定后，新建仓库需使用 GitHub 网页等可用方式，先核验登录账号和私有可见性，再初始化内容。这个能力差异不影响本地清单、迁移分支准备和代码审阅。
