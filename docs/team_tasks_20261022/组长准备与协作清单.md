# InkStruct 组长准备与协作清单

发布日期：2026-10-22。分工：组长负责生成主线、公共接口、集成发布及写字机实测；另外四名成员分别组成字集研究与评测组、Android 开发组。

下发时，字集组接收[本组任务书](字集研究与评测组任务书.md)与[共用附件](共用接口与验收约定.md)，Android 组接收[本组任务书](Android开发组任务书.md)与同一附件。建议整体发送本目录，保留文档之间的相对链接。本清单供组长安排资源与验收。

## 一 开工前必须准备

| 准备项 | 应提供的具体内容 | 满足条件 |
| --- | --- | --- |
| 当前源码基线 | 工作树完整快照、真实 HEAD、修改与未跟踪文件清单、逐文件哈希、运行与安装说明 | 包含新增加的 v6.2、字表和桌面文件；不能仅 clone 当前提交，也不把个人数据混入公共源码包 |
| 生成资源 | 结构数据库一致性副本、源数据与许可证、修正规则、具名字表目录 | 记录结构逻辑身份和文件哈希；数据库含已提交 WAL 内容；两组使用相同修正规则 |
| 参考资源 | 与冻结生成基线一致的笔数、笔顺及参考坐标，含来源许可、版本和缺口 | 对少量修正字先核验一致；不能直接假定原始数据库导出与当前修正生成相同 |
| 运行入口 | 已验证的小型 v6.2 导入、建档、生成示例及依赖清单 | 显式指定 `v62`，给出真实输出协议和资源身份；旧 CLI 默认和旧验收脚本不能代替 |
| 作者身份 | 允许参与的作者 ID、显示名称映射、原始批次与用途 | 两组共享稳定 ID；姓名映射可由组长单独保管，设备切换不创建同人不同作者 |
| 设备安排 | 至少一台带配套笔的 Android 平板和一台 Android 手机，型号、系统版本、笔型号及借用计划 | 平板笔、平板手指、手机手指均可真机检查；设备不全时标出对应待验收范围 |
| 协作安排 | 四名成员角色、代码位置、评审与合并方式、阶段日期、问题登记入口 | 两组可直接联调，你审核公共协议和生产改动，成员自行定位日常问题 |

桌面现有应用版本为 0.1.40。本轮仅新增任务文档，不升级版本、不生成应用包。后续交付构建由你统一递增 `APP_VERSION`，同步说明和发布文件名；Android 的 `versionName` 从同一版本源派生，`versionCode` 单调递增。首次成员交付构建前分配新应用版本，M0 固定跨仓库读取版本源的方式。

## 二 首次实验前准备

1. 整理可供成员使用的最小作者样本包，明确作者允许的使用和分享范围。优先提供只读副本与脱敏映射；既有样本、评分和字体均保留，不以“整理数据”为由覆盖原件。
2. 列出历史数据污染风险。`artifacts/v61_collection_acceptance_20261013/run_v3_with_validation/source_archive.json` 含验证用途样本，不能直接作为独立质量基线。让字集组从可追溯原始样本重新划分并建档。
3. 给字集组数据库存清单：每位作者的不同字数、重复份数、可用输入方式、已有时间／压力元数据。没有的字段明确写缺失，避免用推断值冒充真实设备数据。
4. 确认录制参与者与时间。完整研究默认至少三位作者、32／64／96 字预算、每位至少 32 个最终验证字；具体采多少训练候选由字集组据已有库存提出。设备差异试验安排同一作者重复参加，并轮换输入方式顺序。
5. 安排至少三名未解盲评分者。两组成员可交叉参与，但不能用已经调过对应方案或看到左右方法映射的人补独立评分人数。先确定能投入的评分量，再冻结试验规模。
6. 准备允许成员运行的计算与存储空间。实验、解包和研究索引使用独立新目录，保留失败记录；明确普通 import 会替换指定作者目标索引，研究不可指向生产档案目录。

## 三 M0 会议需要固定的决定

M0 的产物是一份两组共同执行的接口样例与日程，不要求先把所有功能开发完成。你维护决定记录，成员落实实现和测试。

- 一级 3500 字目标、S／U 缺口、第一轮候选边界与 v6.2 基线身份。
- 共用附件的新任务清单、批次清单、ID、用途、修订和压力旁附规则；用一个正常例子和几个错误例子对齐。
- 字集组负责方案导出与字符分组，Android 组负责批次导出、校验和活动样本提取；涉及生产索引与协议的改动由你审核。
- Android 最低系统版本、首批支持机型、工具链、源码目录、安装包版本和真机资源。
- 研究的主要指标、预算、验证字符冻结方式、盲评与统计口径；数据不足时的缩减方案。
- 两组分别列出 M1 至 M3 负责人、日期和依赖。每周至少一次联合检查，阻塞与接口问题平时直接登记处理。

当前任务书已给出可开工的范围和默认规模；上述决定用于结合实际资源执行，不需要你逐条重新设计。公共协议之后若变化，记录修订并重跑相关兼容测试。

## 四 你保留的验收责任

| 节点 | 你检查什么 | 小组应先提供什么 |
| --- | --- | --- |
| M0 | 基线真实、资源一致、接口可实现、实验范围可负担 | 各组计划、数据／设备缺口、最小交换例子 |
| M1 | Android 实采能进入当前 v6.2，验证字未进入供体 | 可安装 APK、样本包、接收与生成命令、逐字来源记录 |
| M2 | 对照公平、真机模式覆盖、失败不被隐藏 | 实验配置与原始统计、盲评材料、故障和设备报告 |
| M3 | 交付可复现、文档可用、是否接入主线 | 可构建源码、推荐任务、脚本、测试结果和已知限制 |
| 写字机 | 尺寸、抬落笔、路径、速度与书写表现 | 已完成数字验收的机器 SVG、预览、参数建议和具体问题 |

把硬件验收集中安排在共同约定的时间窗口。你返回实际参数、照片／视频和问题编号，交对应小组分析；不承担替成员重做实验整理、批次转换或普通 Android 调试。

## 五 首轮启动顺序

先准备源码与资源快照、明确两组角色和可用设备，再召开 M0。随后让字集组给出 16 至 32 字小任务及独立验证任务，Android 组完成真实录制与导出，两组一起做接收、v6.2 生成与来源检查。小闭环通过后，你做一次有限写字机验证，再放大研究规模和设备测试。

正式下发后，两组都应能在无写字机、无组长实时陪同的情况下完成大部分工作；最终集成、版本发布和硬件结论仍由你负责。
